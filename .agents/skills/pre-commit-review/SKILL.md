# Pre-Commit Review

## 定位与边界

这是一个只读的提交前 code review skill。它审查当前 Git 变更，产出可以直接定位和验证的审查意见。

- 仅在用户明确点名 `/pre-commit-review`、`$pre-commit-review`，或明确要求“使用 pre-commit-review skill”时启用。普通的“看下代码”不自动启用本 skill。
- 默认审查 staged、unstaged 和 untracked 变更；用户指定 commit、分支或 diff 范围时，以用户指定范围为准。
- staged 与 unstaged 重叠时，分别标注“提交候选”和“工作树额外改动”；不要把未暂存内容当成即将提交的内容。
- 只看变更行和验证问题所需的直接上下文。未被本次变更触及的历史问题不单独报告，除非变更暴露了回归或使其变得可达。
- 不编辑、删除、格式化、暂存、贮藏、切换分支或提交；不安装依赖、改 lockfile、启动 watch/dev server、部署或执行会改变仓库状态的命令。
- `git-commit` / `quick-commit` 负责提交；普通编码流程负责修复。用户要求修复时，退出本 skill 的只读边界后再处理。

## 审查模式与速度策略

默认使用 **Standard** 模式：完成变更集、直接上下文和必要的受影响包检查。不要因为 skill 被调用就自动运行根目录全量测试、全量 lint 或生产构建。

按变更路径选择最小检查集：

- 只有 Markdown、CSS、静态资源或文档变更：保留 `git diff --check`；只有当 HTML、构建配置或资源注入受影响时才构建。
- 单个 package 内的 TS/TSX 变更：运行该 package 已声明的 no-emit 类型检查和测试；lint 限定到变更的 TS/TSX 文件。
- HTML、入口、bundler/Vite 配置、虚拟模块、产品配置或资源路径变更：在 package 类型检查和测试之外运行该 package 构建。
- 共享 package、协议、workspace 配置、lockfile 或跨 package 路径变更：按依赖范围升级到根目录类型检查和相关 package 测试；只有用户要求 CI 级验证或依赖图无法局部覆盖时才运行全量测试。

只有以下情况升级到 **Full** 模式：用户明确要求完整/CI 级验证、变更跨越多个 workspace 且无法局部覆盖、或 Standard 检查暴露了需要更广范围验证的失败。报告中说明升级原因。

批量读取和检查时避免重复工作：

- 用一次批量命令取得 status、两侧 stat/name-status、untracked 路径和两侧 `diff --check`；不要在输出截断后重复读取同一份完整 diff。
- 先看 diff 元数据，再用 `git diff --unified=3` 阅读变更行及直接上下文。未跟踪文件才按全文阅读；大 CSS/生成物不因文件被触及就全文展开。
- 不要同时运行覆盖同一 package 的 package 测试与聚合测试，也不要同时运行 package 类型检查和已经包含它的根目录类型检查。
- `git diff --find-renames HEAD` 只在存在删除、重命名、二进制或普通 diff 无法解释的路径时使用。
- 命令输出以结论为主，保留失败位置和必要摘要；避免把完整构建日志或重复测试日志带入审查上下文。

## 证据规则

每条 finding 必须同时说明类别、位置、现象、影响、严重度和推荐方向，并能由 diff、调用方、配置或命令输出复核。架构、设计和“优雅/简练”相关意见同样必须落到具体依赖、复杂度、重复、边界或维护成本，不能只写审美判断。

- 未跟踪文件没有 diff 基线：把文件全文视为变更，并检查是否应纳入本次任务。
- 不把“没有搜到引用”直接当成死代码。考虑 public API、动态导入、反射、代码生成、配置驱动和测试入口；证据不足时降为 `Question` 或不报告。
- 不把格式偏好、个人命名偏好或未经证实的未来风险当成 finding。重复问题合并为一条，按最小可复现影响描述。
- 无法从当前上下文判断是否属于任务范围时，列为 `Question`，不要武断标记为无效变更。
- 生成物、第三方 vendored 代码、依赖目录和构建产物不纳入审查，除非它们本身被用户指定为交付物。

## 严重度

- **Block**：本次变更明确造成构建/类型失败、功能错误、数据损坏、权限或安全回归，或破坏必要的发布门禁。
- **Should Fix**：高可信的正确性、资源释放、接口契约、配置覆盖、架构耦合、错误抽象或测试缺口问题，提交前应处理。
- **Nice to Fix**：不影响当前行为，但会造成明确维护成本、认知负担或重复复杂度；必须有具体改进收益。
- **Question**：需要用户确认的语义、兼容策略、任务范围或架构取舍；不把它伪装成缺陷。

## 工作流

### 1. 建立准确的变更集

先确认仓库根目录和当前状态，再分别读取 index、工作树和未跟踪文件：

```sh
git rev-parse --show-toplevel
git status --short
git diff --stat
git diff --cached --stat
git diff --name-status
git diff --cached --name-status
git ls-files --others --exclude-standard
git diff --check
git diff --cached --check
```

有 `HEAD` 时，仅在存在删除、重命名、二进制或普通 diff 无法解释的路径时用 `git diff --find-renames HEAD` 辅助理解整体变化；初始提交或无 `HEAD` 时不要假设该命令可用。对删除、重命名、二进制和未跟踪路径分别确认状态，不要只看统计数字。

### 2. 探测项目约定

只读取与变更相关的项目描述和配置，识别实际可用的：

- 包管理器、workspace/root filter 和 lockfile；
- lint、格式化、类型检查、测试和构建脚本；
- `tsconfig`/编译器引用、bundler alias、环境变量和入口；
- hook、CI pipeline、`.gitignore` 以及新增包的覆盖范围。

优先使用仓库已经声明的脚本和工具，不凭经验拼装命令，不安装新工具。配置文件只有在本次变更触及它们、或它们决定变更能否被检查/构建时才深入审查。

### 3. 审查变更

按下面的顺序检查，重点关注变更引入的行为和契约：

1. **构建与接口契约**
   - import/export、路径重命名或删除后的所有调用方、类型和 schema 是否同步；
   - API 字段、错误码、序列化格式和默认值是否与既有消费者一致；
   - package script、workspace filter、lockfile、`tsconfig` references、alias、环境变量、hook 和 CI 是否仍覆盖新路径。

2. **运行时正确性与资源生命周期**
   - null/空集合/边界值、错误传播、并发、重试、取消和权限路径；
   - listener、subscription、timer、stream、文件句柄、数据库连接和临时目录是否在成功、失败、取消和卸载路径释放；
   - 新增兼容分支是否有明确期限、消费者或测试，而不是无条件保留旧字段。

3. **架构与设计合理性**
   - 模块职责是否清晰，新增逻辑是否放在正确的层；依赖方向是否符合现有分层，是否引入不必要的反向依赖、跨层调用或循环依赖；
   - 数据、状态和错误的所有权是否明确，是否产生重复 source of truth、隐式全局状态、过宽的共享接口或泄漏内部实现的 API；
   - 抽象是否由真实变化点驱动，接口、factory、wrapper、泛型和配置层是否与复杂度相称；是否把一次性逻辑过早抽象，或把本应复用的契约复制到多个位置；
   - 扩展点、兼容层和边界是否有清晰不变量；设计是否能被现有测试、日志和故障处理路径观察和验证；
   - 评估设计时允许读取相关调用方和相邻模块，但不把本次变更扩大成无关的架构重构。无法在当前上下文裁决的取舍列为 `Question`，并说明选项及代价。

4. **代码质量、可读性与简练度**
   - 控制流是否表达主路径，是否有不必要的嵌套、分支、状态转换、临时变量或重复转换；简练以降低偶然复杂度为目标，不以压缩行数或牺牲可读性为目标；
   - 命名、函数/组件大小、参数数量、返回值和错误模型是否表达真实契约；相邻代码已有约定时优先保持一致；
   - 专有名词和缩写在驼峰/帕斯卡命名中是否保留规范大小写，例如 `UI`、`JSON`、`HTML`、`SDK`、`APP`、`API`、`URL`、`HTTP`、`XML`、`CSS`、`JS`、`TS`、`CLI`、`CPU`、`GPU`、`SQL`、`UUID`、`DOM`、`YAML`、`SVG`、`SSE`、`DNS`、`MCP`、`ACP`、`OpenAI`；不要把它们写成 `Ui`、`Json`、`Html`、`Sdk`、`Api`、`Url`、`Http`、`OpenAi` 等。按语言惯例保留首词小写、品牌/平台的正式拼法和第三方 API 的既定导出名（如 `IncomingHttpHeaders`）；区分代码符号与 JSON/HTTP/命令等外部协议字段，除非用户明确要求并确认兼容性影响，不因命名偏好改动协议字段。
   - 重复逻辑是否会产生漂移，局部 helper 是否真的消除重复或隔离复杂度；注释是否解释原因、不变量和外部约束，而不是复述代码；
   - 代码是否容易测试、调试和修改，是否存在隐藏副作用、过度魔法、无效兼容代码或难以验证的隐式行为；
   - 只有能指出具体复杂度、重复、耦合、认知负担或维护后果时，才报告“不够优雅/不够简练”。

5. **死代码与无效范围**
   - 未使用的局部变量、不可达分支、孤立状态、被注释掉的代码、过时 TODO 和只为一次调用增加的抽象；
   - 变更是否混入与任务无关的重排、格式化、批量重命名或生成物；范围判断必须结合用户目标、提交信息或文件内容。

6. **测试与验证能力**
   - 行为改变是否有合适的单元、集成或端到端覆盖；测试是否验证契约而不是实现细节；
   - fixture、mock、参数化用例和 snapshot 是否与真实 schema/边界一致，是否掩盖失败；
   - 变更是否新增了无法由仓库现有命令检查的路径。

### 4. 运行安全检查

在不改变仓库状态的前提下运行必要检查：

- 始终保留 `git diff --check` 结果；
- 仅使用项目已声明且范围明确的 lint、no-emit 类型检查或测试命令；优先限定到受影响的 package/path；
- 跳过安装依赖、更新锁文件、watch、开发服务器、部署、数据库迁移和其他已知会写入或产生长期进程的命令；
- 命令未运行、运行失败或只覆盖部分变更时，在报告中明确写出原因和剩余风险；命令全绿也不能替代代码审查。

## 报告格式

按严重度从高到低输出 findings，位置按文件和行号排序；最后给总览和验证摘要。没有某一等级时明确写“无”。

```markdown
## Block
- `[架构] path/to/file.ts:42`：现象。影响：...。证据：...。推荐：...

## Should Fix
- `[运行时] path/to/file.ts:42`：现象。影响：...。证据：...。推荐：...

## Nice to Fix
- `[代码质量] path/to/file.ts:42`：现象。影响：...。推荐：...

## Question
- `[设计] path/to/file.ts:42`：需要确认的语义或范围，以及两种选择的影响。

## 总览
- 变更范围：staged / unstaged / untracked，文件数和增删行数
- 工程约定：包管理器、相关 lint/typecheck/test/build 命令
- 已执行检查：命令及结果；未执行检查及原因

## 配置与验证摘要
- 构建/类型/测试/lint、hook、CI、lockfile 和 `.gitignore` 的覆盖结论
```

报告要求：

- 先给 findings，再给简短总览；Block 和 Should Fix 必须优先；
- 一条 finding 只描述一个可行动问题，推荐方向不要展开成实现计划；
- 没有可信问题时，明确写“无可确认 finding”，并保留检查未覆盖的风险；
- 不因为用户没有提供完整业务背景而虚构结论；将缺失信息列为 `Question`。

## 与其他 skill 的关系

- 不接管 `git-commit` / `quick-commit` 的分支、暂存、确认和提交流程。
- 不自动调用 `execute-plan` / `plan-as-html`，也不把 review 结果伪装成实施计划。
- 不因当前位于 `main`、`develop` 或其他保护分支而阻止只读审查；分支保护只约束会修改历史的操作。
